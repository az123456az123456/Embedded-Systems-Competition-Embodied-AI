# IMU + 双目 OV5640 1080p 合并工程

> 2026-10-12 · ACG138 / GW5AT-LV60PG484AC1/I0
>
> 已附联调位流：功能仿真和同一时钟域时序通过；跨时钟、复位及板级I/O时序尚未完成确认，未上板验收。详见 `BUILD_STATUS.md`。

## 📦 入口

打开 **`imu_camera_dual_1080.gprj`**，顶层 **`imu_camera_dual_top`**。

这是可独立复制、编译的合并工程，所有 Verilog、Gowin FIFO/PLL IP、AF 固件、引脚和时钟约束均在此目录，不依赖原工程的相对目录。原 IMU 和摄像头工程未被覆盖。

| 功能 | 合并后的行为 |
|---|---|
| 双目 OV5640 | 保留每路960×1080中央裁剪、左右合成1920×1080 RAW、行配对和自动对焦 |
| 摄像头输出 | 保留 IPv4 / UDP 6102，源192.168.0.2、目的192.168.0.3及原摄像头 MAC |
| MPU9250 | 保留加速度、陀螺仪、AK8963磁力计、温度和I²C错误检查 |
| IMU 输出 | 保留原始以太网 EtherType 0x88B5、IMU9载荷和原IMU MAC |
| 共用RGMII | 一个125MHz时钟、一个ODDR输出组；两类完整帧依次发送 |
| RK3588 程序 | 继续使用原双目接收/ISP程序及 IMU 窗口，两者可同时运行 |

本版本是**双目常规无补光**版本，不包含电机控制或原 PCIe 功能。

## 🔌 接线

摄像头两路引脚全部沿用资料包 `14_FPGA_摄像头1080p` 的 `camera_dual.cst`，不调整已接好的摄像头排针。IMU 使用 P10：

| MPU9250 | ACG138 | FPGA球位 |
|---|---|---|
| VCC | P10-22，3.3V | 电源 |
| GND | P10-21 | 地 |
| SCL | P10-1 | D16 |
| SDA | P10-2 | E16 |

SCL/SDA 为开漏，沿用模块到3.3V的上拉；没有上拉时各加约4.7kΩ。不接5V。

LED D0闪烁表示IMU采集逻辑运行；D1表示六轴数据有效；D2表示磁力计数据有效；D3表示IMU异常/数据超时。摄像头状态仍通过原C13诊断串口输出。

本工程共有46个物理信号脚，已核对无重复球位。P10-4/5/6/7不用于本工程，但加载此位流不会保留以前的电机控制逻辑。独立联调时关闭电机驱动电源。

## 🛠️ 编译

建议将整个工程解压到简单英文路径，例如 `D:\imu_camera_dual_1080`，避免Gowin工具在中文路径中的兼容问题。

推荐在 Gowin Tcl Console 或 `gw_sh` 中执行：

```tcl
source build.tcl
```

或在工程目录执行：

```sh
gw_sh build.tcl
```

构建脚本设置：

- 器件：`GW5AT-LV60PG484AC1/I0`；顶层：`imu_camera_dual_top`。
- `enable_dsrm=1`、`use_cpu_as_gpio=1`，沿用摄像头工程的必要选项。
- 输出名称：`imu_camera_dual_1080`。
- 成功生成后的位流位置：`impl/pnr/imu_camera_dual_1080.fs`。

GUI的相同配置随 `impl/imu_camera_dual_1080_process_config.json` 提供。若重新建立工程，必须重新确认上述选项。AF固件读取 `camera/ov5640_af.hex`，不要只复制顶层 `.v`。

Gowin Linux工具需要本机许可证；无图形环境可使用 `QT_QPA_PLATFORM=minimal QT_QUICK_BACKEND=software`，并清除失效的 DISPLAY。编译不会自动连接或烧写开发板。

## ▶️ 板端使用

1. 保持目前已能运行双目摄像头的 RK3588 Buildroot/设备树/网卡配置。
2. 用 Gowin Programmer 将合并位流下载到 SRAM，测试时不必写入 Flash。
3. 按原教程运行 `dual-1080` 摄像头接收与显示。
4. 另外启动之前的 IMU 窗口 `./run-imu.sh`。若需指定网卡，使用原来成功收数据的同一接口。

不要再下载独立IMU或独立摄像头位流，否则会替换整个FPGA配置。也不应同时启动两个争用UDP 6102的摄像头接收进程。

合并版本发送时钟采用**原摄像头PLL的125MHz**。这与独立IMU工程使用RK输入时钟不同，但对RK端接收协议没有变化。板内RGMII为1.8V，ODDR连接方式沿用摄像头工程；未使用E19输入脚。

## 🔧 合并细节

- `rtl/imu_camera_dual_top.v`：统一双目、IMU、串口诊断和RGMII顶层。
- `rtl/gmii_frame_share.v`：完整帧调度；IMU请求在下一个可用边界获得发送机会，不打断图像帧。
- `camera/ov5640x2_udp_rgmii.v`：导出原摄像头GMII数据和PLL时钟，模块名改为`camera_dual_gmii`。
- `camera/controller.v`：FIFO读取使能采用并行译码，保持原行配对和丢行恢复行为。
- `camera/UDP_Send.v`：增加`tx_allow/tx_busy`，只在开始一帧前等待授权；帧后等待默认改为12个125MHz时钟，可通过`FRAME_GAP_CYCLES=256`恢复原节奏。修正原FIFO计数接口的12/13位不匹配。
- 摄像头初始化完成状态经过两级寄存器同步到125MHz，避免直接跨域控制共用发送调度。
- `imu/imu_gmii_source.v`：保留原IMU快照及LED，发送请求等待授权时不提前确认mailbox。
- `imu/imu_ethernet_tx.v`：载荷改为逐字节移位并提前寄存移位使能，CRC使用已寄存的发送字节，缩短组合路径；帧内容和CRC不变。
- 摄像头诊断串口与自动对焦状态统一使用摄像头PLL的50MHz，波特率保持原值。
- `camera/gmii_to_rgmii.v`：两类数据最终共用唯一一组6个ODDR。
- SDC仅对mailbox的同步器入口设置例外，并对保持数据到接收寄存器的路径设置12ns最大延迟；没有把全部50/125MHz路径直接忽略。

IMU正常约每秒200个小帧，对链路增加约0.2Mbit/s负载。摄像头大帧（1922字节UDP载荷）和已有MTU/ISP配置保持原样。实际双目帧率仍需在板上联调测量，不能用单独两份工程的记录替代合并版本验收。

```sh

```

仿真覆盖：

- 使用实际修改后的摄像头UDP发送器与实际IMU以太网发送器并发发送，检查不碰撞、不切断帧、跨来源帧间隔≥12字节时钟。
- 独立Python检查所有摄像头行字节、IPv4校验、UDP端口、IMU载荷和Ethernet CRC32。
- 原双目行配对测试覆盖全部1080行，包括1023行以上行号。
- MPU9250九轴、初始化、NACK、溢出、断线、SCL超时、器件ID和地址回退。
- 合并后的IMU源在发送被阻塞时保持请求；验证LED、过期状态、心跳和DDR半字节顺序。

加密的Gowin FIFO在发送仿真中使用FWFT行为模型；实物IP仍由Gowin编译。仿真不是实际摄像头、RK接收吞吐或I/O时序验证。最新Gowin编译结果和剩余限制见 `BUILD_STATUS.md`。

## 2026-10-15 RGMII 发送调度优化

摄像头 `UDP_Send` 原先每个行包结束后等待256个125MHz时钟，并在此期间阻塞IMU授权。现在使用参数 `FRAME_GAP_CYCLES`，默认12，低于12的设置自动钳位到12；流水线和状态切换还会增加少量空闲周期。协议、1922字节UDP载荷、MAC/IP/端口及IMU优先级均保持兼容，RK3588原ISP接收程序和统一窗口无需改协议。

每行固定等待减少244个时钟，即1.952微秒；1080行累计减少约2.108毫秒的发送端等待。这是链路持续有数据时的理论开销节省，不代表实测帧率增幅。并发仿真中IMU最大等待由2179降到1935个时钟（17.432到15.480微秒），仅代表该测试激励。

`make test` 分别验证默认12、兼容256、非法偏小值1（钳位12），检查帧间隔至少12、不抢断、无FIFO下溢、逐字节图像及CRC。也回归完整1080行、IMU采集和DDR输出。

本次仅更新源码和仿真，目录中已有位流与时序报告属于优化前版本。部署前需重新执行 `gw_sh build.tcl` 并检查时序，然后在RK3588复用原接收环境，比较相同场景下的帧率、图像丢行、网卡丢包及IMU更新。若板端接收来不及处理更密集的包，可将发送器参数恢复256后重新构建。尚未连接实物，不宣称已解决板级RGMII时序或驱动丢包。
